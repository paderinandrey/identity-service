# cache-user-lookups

## Why

`/internal/session/validate` вызывается входным proxy на каждый запрос любого пользователя экосистемы — это самый горячий путь сервиса. Сейчас он делает SELECT в PostgreSQL на каждый вызов: `ActiveChecker` уже загружает всю строку пользователя, но кеширует из неё только булев `active`, а хендлер следом грузит ту же строку заново. На промахе кеша — два одинаковых запроса, на попадании — один. Кеш с нужной семантикой уже существует, просто хранит не то.

## What Changes

- `identity.ActiveChecker` становится `identity.UserCache`: кеширует `*User` целиком на ту же задержку отзыва (`USER_REVOCATION_DELAY`), отдаёт и признак активности, и саму запись. Отсутствующий пользователь кешируется как отрицательный результат, чтобы промахи не били по БД.
- `userSource` в wiring берёт `FindByID` из кеша: validate на прогретом кеше перестаёт ходить в PostgreSQL совсем.
- Тесты счётчика обращений: N вызовов подряд → ровно одно обращение к хранилищу; после TTL — новое. Плюс тест уровня хендлеров: validate обращается к источнику пользователя ровно один раз за запрос.

Не входит: кеширование в GraphQL-резолверах справочника (там нужны свежие данные и запросы редки), k6-скрипты нагрузки.

## Capabilities

### Modified Capabilities

- `web-sessions`: контекст пользователя в `/auth/me` и внутренней проверке сессии может отставать от базы не более чем на задержку отзыва — то же ограничение, что уже действует для признака активности.

## Impact

`internal/identity` (кеш), `cmd/identity-service` (wiring), тесты. Внешних зависимостей и изменений API нет.
