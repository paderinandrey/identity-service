# graphql-limits — Design

## Context

`NewServer`: `handler.New` + `transport.POST{}` + `Introspection` за
`authMiddleware`. `users(search, includeInactive)` → `SearchUsers(…, 200)`,
`ORDER BY name, email LIMIT 200`. `User.roles` — резолвер с отдельным
`UserAssignments` на каждого пользователя. `http.Server` только с
`ReadHeaderTimeout: 5s`.

## Decisions

1. **Лимит тела — `http.MaxBytesReader` в обёртке над gqlgen-хендлером**,
   1 MiB как у SCIM. Превышение gqlgen сам превращает в JSON-ошибку
   транспорта; резолверы не вызываются.

2. **Сложность считается с множителями списков.** Дефолтный подсчёт gqlgen
   даёт списку стоимость одного элемента, поэтому лимит без множителей
   ничего не ограничивал бы. `Complexity.Query.Users = child × first`,
   `Complexity.Query.AccessAuditLog = child × limit`, `applications` —
   `child × 20` (справочник маленький, но с вложенными ролями). Лимит
   `2000`: страница в 200 пользователей с ролями (~5 полей + roles ≈ 8
   на пользователя) укладывается; десять таких алиасов — нет. Алиасы
   суммируются самим gqlgen.

3. **Курсор — keyset, не offset.** Порядок `(name, email, id)`; курсор —
   base64 от JSON этих трёх значений последнего узла. `after` неверного
   формата → `BAD_USER_INPUT`. `first` вне `[1, 200]` → `BAD_USER_INPUT`.
   Хранилище запрашивает `first + 1` строк, чтобы знать `hasNextPage`
   без второго запроса. Offset отвергнут: сдвигается при изменениях и
   дорожает с глубиной.

4. **Prefetch вместо dataloader.** В контекст запроса `authMiddleware`
   кладёт указатель на request-scoped кеш назначений; `users`
   резолвер после выборки страницы загружает назначения всех её
   пользователей одним `WHERE user_id = ANY($1)` и наполняет кеш;
   `User.roles` берёт из кеша, а при промахе (одиночный `user`,
   `_entities`, мутации) запрашивает как раньше. Dataloader с
   батчингом по таймеру отвергнут: он тянет зависимость и полагается на
   параллельное исполнение полей, а prefetch детерминирован и
   проверяется простым счётчиком запросов.

5. **Таймауты сервера**: `ReadTimeout 30s` (тело SAML/SCIM до 1 MiB
   читается за секунды), `WriteTimeout 30s` (ни один запрос не должен
   жить дольше; validate — миллисекунды), `IdleTimeout 120s` для
   keep-alive от proxy. Значения константы: это свойства сервиса, не
   окружения.

## Risks / Trade-offs

- Смена формы `users` ломает единственного известного клиента —
  Yaak-запрос владельца; стенд и стаб-сабграф поле не используют.
- `WriteTimeout` жёстко оборвёт ответ дольше 30 с; сегодня таких путей
  нет, а появление такого пути — повод для отдельного решения, не для
  снятия лимита.
- Бюджет сложности — грубая оценка; его назначение — отсечь заведомо
  абсурдные запросы, а не точно моделировать нагрузку.
