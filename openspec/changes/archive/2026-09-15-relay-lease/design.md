# relay-lease — Design

## Context

`drainOnce`: одна транзакция — `SELECT … FOR UPDATE SKIP LOCKED` (100
строк) → publish с confirm по каждой → `published_at` → commit. Ошибка на
строке: `attempts+1`, остаток пачки не публикуется, следующий цикл снова
начинает с той же строки. `mandatory=false`. `outbox_pending` обновляется
только после непустой пачки. Опубликованные строки не удаляются. Две
реплики по умолчанию.

## Decisions

1. **Три коротких шага вместо одной длинной транзакции.**
   *claim*: `UPDATE … SET lease_until = now() + lease, leased_by = $me
   WHERE id IN (SELECT … FOR UPDATE SKIP LOCKED) RETURNING …`, commit.
   *publish*: вне транзакции, с confirm, по одной. *settle*: одна короткая
   транзакция на пачку — `published_at` успешным, `attempts+1`,
   `last_error`, `lease_until = now() + backoff(attempts)` неудачным.
   Просроченная аренда (`lease_until < now()`) делает строку снова
   доступной: реплика, умершая посреди публикации, ничего не блокирует.
   Дубликат при истёкшей аренде возможен — доставка и так at-least-once,
   консьюмеры дедуплицируют по `message_id`. Аренда 5 минут при пачке 25
   и таймауте публикации 5 с — с запасом больше худшего случая.

2. **Порядок на пользователя — условие выбора, а не режим работы.**
   Строка eligible, только если у её `user_id` нет более раннего
   `(created_at, id)` неопубликованного и некарантинного события. Так
   каждая пачка содержит не более одного события на пользователя, а
   следующее берётся только после фиксации предыдущего — на любой реплике.
   Это и делает обещание спеки истинным для `replicaCount: 2`.
   Пропускная способность: один раунд на событие пользователя; для
   событий изменений пользователей это ничего не стоит. Для `user_id`
   нужна колонка (миграция `00009`) и backfill из payload (`00010`,
   данные; таблица маленькая, один `UPDATE`).

3. **Backoff и карантин.** `backoff(attempts) = min(2^attempts с, 5 мин)`;
   после `maxAttempts = 10` — `quarantined_at = now()`. Карантинная
   строка не участвует в выборке и **не блокирует** более поздние события
   своего пользователя: иначе одна битая строка отключила бы пользователя
   от проекций навсегда. Цена — консьюмер увидит разрыв версий; `user.
   version` для этого и существует, а `replay-users` восстанавливает
   проекцию. Возврат из карантина — `requeue-events` (сбрасывает
   `quarantined_at`, `attempts`, `last_error`), после того как оператор
   понял причину по `last_error`.

4. **`mandatory=true`, возврат — это ожидание, а не отказ.** Брокер
   подтверждает сообщение, которое не попало ни в одну очередь; сейчас
   такое событие считается доставленным и теряется для будущих
   консьюмеров. С `mandatory` брокер возвращает его (`basic.return`
   приходит раньше `basic.ack`). Возврат классифицируется как
   *неразмеченность*: `attempts` не растёт, строка получает максимальный
   backoff и ждёт, когда консьюмер объявит и привяжет очередь; метрика
   `outbox_unroutable_total`, `warn` в логе. Так деплой identity раньше
   GSH/DFM не теряет и не карантинит события. Топология: сервис владеет
   только exchange (`topic`, durable); очереди и bindings объявляют
   консьюмеры — записано в README как контракт.

5. **Retention из цикла relay**, раз в час: `DELETE … WHERE published_at
   < now() - $retention` пачками по 1000, пока удаляется полная пачка.
   `OUTBOX_RETENTION` (default `720h`). Опубликованные строки — локальный
   след «что и когда ушло», полезный при разборе отставшей проекции;
   30 дней — осознанный выбор, не предел.

6. **Метрики честны при аварии.** Gauges `outbox_pending`,
   `outbox_quarantined`, `outbox_oldest_pending_age_seconds` обновляются
   в начале каждого цикла, до попытки соединения с брокером. Счётчики
   `events_published_total`, `event_publish_errors_total`,
   `outbox_unroutable_total`.

7. **`Publisher` — интерфейс у потребителя** (`events.Publisher`: `Publish(ctx,
   Message) error`, `Close()`), AMQP-реализация по умолчанию. Нужен, чтобы
   тесты карантина и backoff подставляли отказывающий публикатор на
   настоящем PostgreSQL, не заставляя RabbitMQ отвечать nack.

## Risks / Trade-offs

- `NOT EXISTS` в выборке — дополнительный индекс
  `(user_id, created_at, id) WHERE published_at IS NULL AND quarantined_at
  IS NULL`; при наших объёмах незаметно.
- Детекция `basic.return` по `MessageId` после `ack` полагается на порядок
  фреймов RabbitMQ (return до ack для mandatory) — документированное
  поведение брокера, публикации последовательные.
- Retention удаляет след: разбор инцидентов старше 30 дней по outbox
  невозможен; логи и метрики остаются.
