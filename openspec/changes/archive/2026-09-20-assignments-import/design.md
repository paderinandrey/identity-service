# assignments-import — Design

## Context

`grant-role` в `main.go` находит активного пользователя по email и зовёт
`AccessStore.GrantRole` — одна транзакция на роль, `ON CONFLICT DO
NOTHING`, журнал только при фактическом изменении. `seed-access`
читает YAML в `access.SeedConfig` с `Validate()` и никогда не трогает
`user_roles`. Все CLI-операции журналируются актором `cli`. Тесты
хранилища доступа — интеграционные, на настоящем PostgreSQL. Мотивация —
proposal.md.

## Goals / Non-Goals

**Goals:**
- Один запуск переносит все назначения GSH; повтор ничего не ломает.
- Отказ по одной записи виден в отчёте и не мешает остальным.

**Non-Goals:**
- GraphQL-мутация массового назначения: API управления — отдельный
  вопрос (спека фиксирует CLI как bootstrap).
- Экспорт `users_roles` из GSH: скрипт живёт на стороне GSH и формирует
  этот файл; формат согласован здесь.
- Снятие ролей, которых нет в файле (reconcile): импорт только добавляет.
  Полная синхронизация — осознанно не сейчас: файл GSH может быть
  неполным, и молчаливое снятие доступа хуже лишнего запуска
  `revoke-role`.

## Decisions

1. **Отдельная команда `import-assignments`, не расширение
   `seed-access`.** Спека и README обещают, что seed никогда не трогает
   назначения; смешивать декларативную схему доступа с данными
   пользователей — путь к тому, чтобы однажды seed их снёс.

2. **Формат файла** — YAML, чтобы не плодить парсеров:
   ```yaml
   assignments:
     - email: ada@example.com
       roles: [gsh/observer, gsh/operator]
     - id: 0f2b7c1a-3d4e-4f5a-8b6c-7d8e9f0a1b2c
       roles: [dfm/engineer]
   ```
   Ровно один из `id`/`email`; `email` допустим потому, что это тот же
   доверенный bootstrap-канал, что и `grant-role` (AGENTS запрещает
   линковать по email в рантайме, не оператору). Пользователь по email —
   только активный (`FindActiveByEmail`), по id — любой существующий
   (`FindByID`): деактивированному переносить роли бессмысленно, но
   явный id — осознанный выбор оператора.

3. **Валидация целиком до записи** — `access.ImportFile.Validate()`:
   синтаксис `app/role`, непустые роли, один ключ, дубликат пользователя
   в файле (две записи на один email/id) — ошибка, чтобы отчёт был
   однозначным. Юнит-тесты без базы.

4. **`AccessStore.GrantRoles(ctx, actor, userID, refs)`** — одна
   транзакция на запись: `findRoleID` + `INSERT … ON CONFLICT DO NOTHING`
   + журнал для каждой роли; неизвестная роль откатывает всё. Возвращает
   число фактически назначенных. Идемпотентность и журнал — как у
   `GrantRole`. Интеграционные тесты: откат при неизвестной роли, повтор
   без новых записей журнала.

5. **Отказы не останавливают импорт.** Неизвестный пользователь или
   роль — строка отчёта `FAIL <кто>: <причина>`, остальные записи
   применяются, код выхода 1 в конце. Альтернатива «всё или ничего» одной
   транзакцией на файл отвергнута: сотни строк под одной транзакцией и
   один опечатанный email блокируют весь cutover, а идемпотентность
   делает частичное применение безопасным для повтора.

6. **`--dry-run`** резолвит пользователей и роли, считает «назначено /
   уже было», ничего не пишет: транзакция открывается и откатывается.
   Реализовано флагом в `GrantRoles` (rollback вместо commit), чтобы
   dry-run проходил тем же кодом.

7. **Отчёт** — по строке на запись: `ok <email|id>: granted 2, already 1`
   или `FAIL …`, итог `import-assignments: N ok, M failed (dry-run)`.

## Risks / Trade-offs

- [Файл GSH содержит email, которых нет в identity-service, потому что
  SCIM ещё не завёл пользователя] → строка FAIL, повтор после
  провижининга; порядок cutover в README: SCIM-импорт → replay →
  import-assignments.
- [Роли GSH не совпадают по именам с seed-файлом] → `FAIL … role not
  found`; исправляется seed-файлом, не импортом.
- [Один и тот же пользователь дважды в файле] → отказ валидации, а не
  «последний победил».

## По итогам ревью Codex (PR #14)

- **P2, один пользователь по `id` и по `email`.** Валидация ловила
  дубликаты только по текстовому ключу; такие записи шли двумя
  транзакциями, и отказ во второй оставлял первую применённой. Теперь
  все записи резолвятся до первой записи в базу, и совпадение
  `user.ID` у двух записей — отказ всего импорта; неизвестные
  пользователи по-прежнему отказ по записи. Сценарий добавлен в спеку.
- **P1, use case в capability-пакете.** Резолв пользователей, отказ по
  совпавшему `user.ID` и сборка отчёта переехали из CLI в
  `access.Import` с интерфейсами `ImportUsers`/`ImportGranter`,
  объявленными у потребителя; CLI разбирает флаги и печатает
  `ImportReport`. Юнит-тесты на фейках: отказ по одному пользователю в
  двух записях без единого grant, независимые отказы записей, проброс
  dry-run.
- **P1, язык документов.** Без изменений: артефакты OpenSpec в этом
  репозитории по конвенции `openspec/config.yaml` (`Language: ru`,
  заголовки и SHALL/MUST — English), как и все архивы с первого дня;
  расхождение с формулировкой AGENTS.md ждёт решения владельца.
- **P2, неожиданные ошибки резолва.** Только `ErrUserNotFound` —
  отказ записи; неверный UUID или ошибка базы прерывают импорт до
  первой записи, чтобы не получить частичный импорт вокруг сбоя.
