# cookie-mutation-origin — Design

## Decisions

1. **Origin-хук на уровне операции, не резолвера.** `AroundOperations`
   видит тип операции (`ast.Mutation`) и заголовки запроса
   (`OperationContext.Headers`); проверка выполняется один раз до
   исполнения и не зависит от того, сколько мутаций в документе.
   Семантика — как у logout: пустой Origin допускается (не браузер:
   router, CLI, тесты), непустой должен быть в доверенном списке.
   Список общий с session (`session.OriginSet`) — одна функция, одно
   правило.

2. **Только мутации.** Query не меняет состояния; проверка на чтении
   ломала бы легитимные cross-origin инструменты без выгоды.

3. **Router обязан пробрасывать Origin.** Иначе сабграф видит запрос от
   router'а без Origin и пропускает его как не-браузерный. На стенде —
   `propagate: origin` в конфиге Cosmo; для прода — требование в README
   к конфигурации router'а. Альтернатива «доверять CSRF-защите router'а» не
   принята: правило AGENTS.md адресовано нам.

4. **Секрет: длина и не-дефолт.** ≥ 32 символов и ≠ dev-умолчанию вне
   development; в development умолчание остаётся, чтобы локальный старт
   не требовал ручной настройки.

5. **`APP_ENV` явный в Kubernetes.** Признак — `KUBERNETES_SERVICE_HOST`,
   который kubelet задаёт каждому поду. Чарт всегда задаёт `APP_ENV`
   (`production` в values.yaml, `development` на стенде), так что guard
   ловит только ручные и чужие манифесты. Проверять «production-подобные»
   URL отвергнуто как эвристику.

## Risks / Trade-offs

- Клиент, который шлёт Origin, но не значится в списке (например, dev-
  инструмент с другого хоста), получит `FORBIDDEN` на мутации — по
  замыслу; список настраивается через `BASE_URL`/`FRONTEND_BASE_URL`.
