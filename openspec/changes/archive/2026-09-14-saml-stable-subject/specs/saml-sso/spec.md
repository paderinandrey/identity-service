# saml-sso — delta

## MODIFIED Requirements

### Requirement: Инициация входа
Сервис SHALL по `GET /auth/saml/init` перенаправлять браузер на SSO-URL Okta с корректным SAML AuthnRequest, запрашивающим NameID формата `persistent`. Идентификатор AuthnRequest SHALL сохраняться в общем для реплик хранилище с ограниченным сроком жизни, чтобы ответ можно было связать с инициированным входом. Параметр `next` (относительный путь возврата) SHALL передаваться через подписанный RelayState. Маршрут MUST быть доступен без существующей сессии. Недоступность хранилища идентификаторов SHALL приводить к ответу 503, а не к входу без отслеживания.

#### Scenario: Переход к IdP
- **WHEN** браузер открывает `/auth/saml/init?next=/orders/42`
- **THEN** сервис отвечает redirect на SSO-URL Okta, AuthnRequest запрашивает persistent NameID, его ID сохранён с TTL, а RelayState содержит подписанный путь `/orders/42` с меткой времени

#### Scenario: Опасный next отбрасывается
- **WHEN** `next` является абсолютным URL, protocol-relative URL или содержит перевод строки
- **THEN** в RelayState сохраняется путь `/` вместо переданного значения

#### Scenario: Хранилище недоступно при инициации
- **WHEN** сохранить ID AuthnRequest не удаётся
- **THEN** сервис отвечает 503 и не перенаправляет на IdP

### Requirement: Обработка ACS-ответа
Сервис SHALL по `POST /auth/saml/acs` валидировать SAMLResponse: подпись сообщения и assertion (SHA-256), срок действия с допустимым дрейфом часов не более 60 секунд, соответствие destination собственному ACS URL и audience — собственному entity ID, ограничение размера сообщения. Ответ SHALL содержать `InResponseTo`, соответствующий ранее сохранённому и ещё не использованному ID AuthnRequest; сопоставление SHALL потреблять этот ID атомарно, так что второй ответ на тот же запрос отклоняется. Ответы без `InResponseTo` (IdP-initiated) SHALL отклоняться, если такой вход не включён конфигурацией явно. При успехе SHALL создаваться сессия и выполняться redirect на путь из RelayState поверх настроенного frontend base URL. Невалидный ответ SHALL отклоняться с 401 без создания сессии.

#### Scenario: Успешный вход
- **WHEN** приходит корректно подписанный SAMLResponse с `InResponseTo` сохранённого запроса для активного пользователя с валидным RelayState
- **THEN** создаётся серверная сессия, браузер получает session cookie и redirect на сохранённый путь поверх frontend base URL

#### Scenario: Невалидная подпись
- **WHEN** подпись сообщения или assertion не проходит проверку
- **THEN** сервис отвечает 401, сессия не создаётся, содержимое assertion не логируется

#### Scenario: Чужой destination или audience
- **WHEN** destination не совпадает с ACS URL сервиса или audience не содержит его entity ID
- **THEN** ответ отклоняется с 401

#### Scenario: Неизвестный или уже использованный InResponseTo
- **WHEN** `InResponseTo` не соответствует сохранённому ID AuthnRequest или этот ID уже был потреблён
- **THEN** ответ отклоняется с 401, сессия не создаётся

#### Scenario: IdP-initiated вход выключен
- **WHEN** приходит ответ без `InResponseTo`, а IdP-initiated вход не включён
- **THEN** ответ отклоняется с 401

#### Scenario: IdP-initiated вход включён
- **WHEN** IdP-initiated вход включён конфигурацией и приходит валидный ответ без `InResponseTo`
- **THEN** вход выполняется; одноразовость assertion при этом сохраняется

#### Scenario: Просроченный RelayState
- **WHEN** RelayState отсутствует, имеет неверную подпись или старше своего TTL
- **THEN** вход продолжается, а путём возврата служит `/`

### Requirement: Сопоставление identity с пользователем
Сервис SHALL находить пользователя по внешней идентичности: провайдер `okta` и стабильный subject из persistent NameID ответа IdP — тот же идентификатор, который поступает через SCIM как `externalId`. Неизвестный subject SHALL получать отказ без создания сессии независимо от совпадения email; привязка по email MUST NOT выполняться; JIT-создание пользователей MUST NOT выполняться. Email из assertion MUST NOT изменять данные пользователя: источник email — провижининг. Расхождение email в assertion с каталогом SHALL фиксироваться в логе идентификатором пользователя без значений адресов.

#### Scenario: Повторный вход по сохранённой идентичности
- **WHEN** приходит ответ IdP с subject, привязанным к активному пользователю
- **THEN** пользователь определяется по привязке независимо от текущего email в ответе и в каталоге

#### Scenario: Первый вход существующего пользователя
- **WHEN** пользователь заведён через SCIM с `externalId` и впервые входит по SAML с persistent NameID того же значения
- **THEN** пользователь находится по этой привязке, новая привязка не создаётся, сессия создаётся

#### Scenario: Смена email в IdP не ломает вход
- **WHEN** у пользователя изменился email в IdP (и, через SCIM, в каталоге), а persistent NameID остался прежним
- **THEN** вход выполняется, email в каталоге не перезаписывается значением из assertion

#### Scenario: Неизвестный пользователь
- **WHEN** subject не привязан ни к одному пользователю — даже если email из assertion принадлежит активному пользователю
- **THEN** сервис отвечает отказом, привязка и сессия не создаются, пользователь не создаётся

#### Scenario: Деактивированный пользователь
- **WHEN** ответ IdP соответствует пользователю с признаком неактивности
- **THEN** вход отклоняется, существующая привязка не удаляется

## ADDED Requirements

### Requirement: Одноразовое принятие assertion
Сервис SHALL принимать каждый assertion не более одного раза: его идентификатор SHALL атомарно фиксироваться в общем для реплик хранилище со сроком жизни не меньше оставшегося срока действия assertion с учётом дрейфа часов. Повторная доставка того же ответа — последовательная или одновременная на разные реплики — SHALL отклоняться с 401 без создания сессии. Недоступность хранилища SHALL приводить к 503, а не к принятию ответа.

#### Scenario: Повтор ответа из другого браузера
- **WHEN** уже принятый SAMLResponse отправляется на ACS повторно с новым набором cookie в пределах срока действия assertion
- **THEN** ответ отклоняется с 401, новая сессия не создаётся

#### Scenario: Одновременная доставка
- **WHEN** один и тот же SAMLResponse одновременно приходит на два экземпляра сервиса
- **THEN** ровно один экземпляр создаёт сессию, второй отвечает 401

#### Scenario: Хранилище недоступно при ACS
- **WHEN** зафиксировать идентификатор assertion не удаётся из-за недоступности хранилища
- **THEN** сервис отвечает 503, сессия не создаётся
