# validate-any-method

## Why

Наш endpoint проверки сессии не соответствовал реальному контракту ext-auth — выяснилось при подключении настоящего Envoy Gateway на локальном стенде. Две несовместимости, каждая из которых отклоняла бы **все** запросы независимо от валидности сессии:

1. Endpoint зарегистрирован как `GET /internal/session/validate`, а Envoy **зеркалит метод исходного запроса**: `POST /graphql` приходит как POST → 405.
2. Настроенный путь Envoy трактует как **префикс** и дописывает к нему исходный путь: фактический запрос — `/internal/session/validate/graphql` → 404.

Обе проявляются только с живым proxy: юнит-тесты и curl вручную ходили ровно тем методом и путём, которые были зарегистрированы.

## What Changes

- Endpoint отвечает на любой HTTP-метод и на любой путь внутри `/internal/session/validate/`: проверка зависит только от cookie, а форму запроса диктует ext-auth.
- Тесты фиксируют оба измерения (метод и подпуть), чтобы привязка не вернулась незаметно.

## Capabilities

### Modified Capabilities

- `web-sessions`: требование о внутренней проверке сессии уточняется — endpoint отвечает независимо от метода запроса.

## Impact

Одна строка в `internal/session/handlers.go` плюс тест и спека. Внешнего API не касается.
