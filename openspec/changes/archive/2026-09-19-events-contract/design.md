# events-contract — Design

## Context

`events.Payload` и `NewPayload` — единственное определение тела события;
relay публикует его как есть с `message_id`, `type`, persistent. README
дублирует JSON-пример руками. Консьюмеров нет; на стенде есть
`dev/stub-subgraph` (отдельный Go-модуль, образ собирается в
`stand-up.sh`, деплоится как `dependencies.<name>` из
`values-local.yaml`). GSH ([[2026-09-18-gsh-integration]]) имеет
inbox-контур с дедупликацией по id события, но без версий и без порядка;
2 воркера × 4 потока обрабатывают события одного пользователя
параллельно. Ветка `relay-lease` (PR #6) меняет `relay.go`/`publisher.go`
и миграции — этот change их не трогает. Мотивация — proposal.md.

## Goals / Non-Goals

**Goals:**
- Один источник правды о теле события: схема, примеры и код не могут
  разойтись незаметно.
- Поведение консьюмера, которое GSH/DFM переносят построчно, доказано на
  стенде против настоящего relay и брокера.

**Non-Goals:**
- Изменения payload (`title`, `last_sign_in_at`) — отдельный change после
  мержа `relay-lease`.
- Свойство `app_id`/`source` в публикации — трогает `Publishing` в
  relay, конфликт с PR #6; консьюмер идентифицирует источник по exchange
  и binding, контракт это фиксирует.
- Персистентная проекция у стаб-консьюмера: у реальных консьюмеров она
  своя (у GSH — `inbox_events` + таблица проекции); стенд доказывает
  правила, а не хранилище.
- Schema registry для событий.

## Decisions

1. **JSON Schema 2020-12 в `docs/events/user-event.schema.json`,
   проверяется в Go-тесте через `santhosh-tekuri/jsonschema/v6`**
   (test-only). Альтернатива без зависимости — сверять только примеры —
   не ловит расхождение схемы с кодом; зависимость одна, без cgo,
   активно сопровождается. Схема строгая: `additionalProperties: false`
   на корне и на `user`, `type` — enum, `id` — uuid, `occurredAt` —
   date-time, `version` — integer ≥ 1.

2. **Примеры генерируются тем же кодом.** Тест строит `NewPayload` с
   фиксированными `id`, `occurredAt` (через подмену часов) и
   пользователем, сериализует и сравнивает с
   `docs/events/examples/<type>.json` байт-в-байт; при `-update`
   перезаписывает. Так пример никогда не «примерно похож» на payload.
   `NewPayload` сейчас берёт `time.Now()` напрямую — добавляется
   пакетная переменная-часы, подменяемая в тестах (единственный
   пакетный state, только для детерминизма тестов).

3. **Референсный консьюмер — `dev/stub-consumer`, отдельный модуль**,
   по образцу `dev/stub-subgraph`: не тянет зависимости сервиса,
   собирается в distroless-образ, деплоится как зависимость стенда.
   Структура — три файла, каждый переносится на Ruby как есть:
   `consume.go` (AMQP: своя durable-очередь `stub-consumer.users`,
   binding `user.#`, prefetch, ack/nack), `apply.go` (чистая функция
   `Apply(state, event) outcome` с исходами applied / duplicate / stale /
   rejected — правила без транспорта, юнит-тесты на ней),
   `http.go` (`GET /projection`, `GET /projection/{id}`, `GET /stats`).
   Дедупликация по id хранится в проекции (множество id), сравнение
   версии и запись — под одним mutex на пользователя, что соответствует
   «атомарно с записью» (в SQL это `UPDATE … WHERE version < $new`
   под row lock — так и описано в документе).

4. **Отказ обработки.** Невалидный JSON или неизвестный `schemaVersion`
   — `rejected`: nack без requeue (в проде — DLQ), счётчик растёт.
   Неизвестный `type` при валидном теле — применяется как снимок:
   контракт говорит, что снимок пользователя полный в каждом событии,
   и это делает добавление типов совместимым.

5. **Стенд.** `values-local.yaml` получает `stub-consumer` (образ
   `stub-consumer:dev`, порт 8080, readiness `/healthz`, env
   `RABBITMQ_URL`); `stand-up.sh` собирает образ. Шаг `stand-verify`
   (после шага 4, SCIM-провижининга): (a) `replay-users` через
   `kubectl run` образа сервиса с ConfigMap-env, затем `GET /projection`
   у консьюмера — каждый пользователь БД присутствует с версией, равной
   `users.version`; (b) SCIM PATCH имени qa-пользователя → в проекции
   новое имя и версия +1; (c) повторный `replay-users` → `stats.stale`
   вырос на число пользователей, проекция не изменилась. Консьюмер
   доступен по Service внутри кластера; шаг ходит к нему из probe-пода
   (как шаги 11–12 в PR #11) или через `kubectl port-forward` —
   выбрать port-forward: проще и не зависит от NetworkPolicy стенда.
   Порядок шагов сохраняет существующую нумерацию, новый шаг вставляется
   после 4 и сдвигает остальные.

6. **README** перестаёт дублировать JSON: ссылка на `docs/events/`.

## Risks / Trade-offs

- [Golden-сравнение байт-в-байт хрупко к порядку полей] → порядок задаёт
  структура Go, `json.Marshal` детерминирован; `-update` переписывает
  примеры осознанно, diff виден в ревью.
- [Стаб-консьюмер живёт в памяти: рестарт пода = пустая проекция] → это
  и есть сценарий «replay на пустую проекцию»; для стенда достаточно.
- [Конфликт с PR #6 по `internal/events`] → добавляется только
  `contract_test.go` и часы в `events.go`; `relay.go`/`publisher.go`
  не трогаются. При мерже #6 раньше — тривиальный rebase.
- [Ложное ощущение, что консьюмер «готов к проду»] → документ и README
  называют его референсом поведения, не библиотекой.

## Migration Plan

Ничего не деплоится: контракт описывает текущее поведение. Стенд —
`stand:up` пересобирает образы и добавляет консьюмер.

## По итогам ревью Codex (PR #12)

- **P1, обещание про неразмеченные события.** Документ утверждал, что
  событие без привязанной очереди «ждёт в outbox» — это верно только с
  mandatory-публикацией из `relay-lease`; на текущем main брокер
  подтверждает и теряет его. Формулировка исправлена: привязать очередь
  до первого нужного события, остальное поднять через `replay-users`;
  mandatory-режим описан как дополнительная гарантия, когда появится.
- **P1, отсутствующее поле `active`.** `json.Unmarshal` даёт `false`, и
  снимок с большей версией деактивировал бы пользователя. Разбор стал
  presence-aware: обязательные поля схемы проверяются по сырому JSON
  до декодирования; тесты на `active`, `occurredAt`, тип вне семейства.
- **P2, закрытый enum типов.** Противоречил правилу «неизвестный тип —
  снимок»: консьюмер, валидирующий по схеме, отверг бы новый тип. `type`
  задан паттерном `^identity\.user\.[a-z]+$`, известные значения — в
  описании; golden-тест дрейфа проверяет тип вне семейства.
- **P2, DLQ.** `Nack(false,false)` без `x-dead-letter-exchange` просто
  уничтожал сообщение. Консьюмер объявляет свой DLX (`<queue>.dlx`,
  fanout) и очередь `<queue>.dlq`; документ говорит это прямо. Побочно:
  аргументы очереди фиксируются при создании — существующую очередь без
  DLX надо удалить или переименовать, стенд это словил.
- **P2, непустая проекция перед replay.** Консьюмер успевал принять
  живые события провижининга; шаг теперь перезапускает консьюмер,
  убеждается, что проекция пуста, и только потом делает replay.
  Дополнительно шаг публикует неразбираемое тело через `rabbitmqadmin`
  и проверяет, что оно легло в DLQ, а `rejected` вырос на единицу.

## По итогам второго ревью Codex

- **P1, `"active": null`.** Проверка присутствия по ключам пропускала
  null, а `bool` декодировал его как false. Разбор идёт через структуру
  с pointer-полями: отсутствие, null и неверный JSON-тип отвергаются
  одинаково; тесты на null `active` и строковую `version`.
- **P2, `additionalProperties: false`.** Запрет ломал совместимое
  добавление полей для консьюмеров со старой копией схемы. Схема
  разрешает неизвестные поля, документ требует их игнорировать, а
  строгость producer'а перенесена в тест
  `TestProducerSendsOnlyDocumentedFields` (сверка ключей payload с
  `properties` схемы на обоих уровнях).
- **P2, полнота валидации.** Парсер принимал не-UUID идентификаторы и
  типы вроде `identity.user.` — то, что схема отвергает. Добавлены
  проверки формата UUID для `id` и `user.id` и полный паттерн типа;
  фикстуры тестов переведены на синтетические UUID.
- **P2, абсолютный счётчик DLQ.** Очередь durable, повторный прогон
  видел сообщение прошлого; шаг запоминает глубину до публикации и ждёт
  роста и глубины, и счётчика `rejected` вместе.
