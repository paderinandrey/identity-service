# harden-session-revocation

## Why

Два подтверждённых дефекта отзыва сессий (обзор Codex 14.09, сверено по
коду и по исходнику scs v2.9.0 в [[2026-09-14-triage-and-plan]]):

1. **Запрос в полёте воскрешает отозванную сессию.** `DestroyAllForUser`
   удаляет ключи сессий и индекс, но не оставляет никакого признака
   отзыва. При `IdleTimeout > 0` scs помечает каждую загруженную сессию
   как изменённую и пересохраняет её в конце запроса (`data.go:81`).
   Запрос, загрузивший сессию до удаления, записывает её обратно после —
   старый токен снова даёт 200. Воспроизведено на настоящем Redis.
2. **Отказ Redis при деактивации скрыт успешным ответом.** SCIM
   `deactivate` сначала снимает `active` в PostgreSQL, затем зовёт
   удаление сессий; ошибка удаления только логируется, ответ 200. После
   реактивации старые сессии снова валидны. Воспроизведено с внедрённым
   отказом `SessionKiller`.

Обе нарушают собственные обещания спек: «после уничтожения прежние
идентификаторы сессий SHALL быть недействительны» (`web-sessions`) и
«сессии SHALL уничтожаться немедленно… реактивация — старые сессии не
возвращаются» (`scim-provisioning`). Общая причина одна: отзыв реализован
как *удаление*, а не как *необратимая отметка*, которую проверяют при
каждой загрузке и сохранении сессии.

## What Changes

- **Поколение сессий пользователя** (`users.session_epoch`, PostgreSQL) —
  долговечная отметка отзыва. Сессия при входе запоминает текущее
  поколение; действительна только сессия с поколением, равным текущему.
- **Деактивация поднимает поколение в той же транзакции**, что снимает
  `active`. Отзыв становится частью долговечного состояния: отказ Redis
  после транзакции не отменяет его, повторная деактивация не нужна.
- **Redis-ограждение**: поколение зеркалится в Redis и проверяется
  обёрткой хранилища сессий при каждой загрузке *и сохранении*. Сессия со
  старым поколением не загружается и не пересохраняется — запрос в полёте
  не может её вернуть. Ограждение ставится до удаления ключей.
- **Реактивация поколение не трогает** — старые сессии мертвы навсегда;
  новый вход получает новое значение.
- Отказ Redis при удалении сессий: долговечный отзыв уже выполнен, ответ
  провижинингу успешный, отказ виден в логах и метрике; проверка сессии
  при недоступном Redis по-прежнему 503, а после восстановления сессии
  отклоняются не позднее задержки отзыва по поколению из PostgreSQL.
- Заодно закрывается drift спеки `access-control`: `EffectivePermissions`
  возвращает пустой набор для неактивного пользователя.

## Capabilities

### Modified Capabilities

- `web-sessions`: уничтожение всех сессий и деактивация формулируются
  через поколение; запрос в полёте не восстанавливает сессию; отказ
  хранилища не отменяет отзыв.
- `scim-provisioning`: деактивация делает отзыв долговечным в одной
  транзакции; реактивация не возвращает сессии; семантика отказа Redis.
- `access-control`: эффективные права неактивного пользователя пусты и на
  уровне метода хранилища.

## Impact

Миграция `00008` (схема, аддитивная, rolling-safe), `identity.User`,
`postgres.Store` (`SetActive` возвращает пользователя, `EffectivePermissions`
фильтрует active), `session` (обёртка хранилища, `Start`/`DestroyAllForUser`
с поколением, проверка в `currentUser`), `graphql` auth middleware, `scim`
`deactivate`, `samlsso`/`e2elogin` — передача поколения при входе. Формат
сессии расширяется полем; существующие сессии без поколения считаются
поколения 0 и остаются валидны, пока пользователю не отзовут доступ.
