## MODIFIED Requirements

### Requirement: Запуск с конфигурацией из окружения
Сервис SHALL читать конфигурацию из переменных окружения при старте: публичный адрес прослушивания HTTP, внутренний адрес прослушивания HTTP, имя окружения (development/staging/production), уровень логирования, строки подключения PostgreSQL и Redis, базовый URL сервиса, URL метаданных IdP, секрет подписи RelayState, базовый URL frontend и параметры сессий (имя cookie, idle-timeout, абсолютный срок, лимит одновременных сессий). Для отсутствующих переменных SHALL применяться безопасные значения по умолчанию, пригодные для локальной разработки; вне development параметры подключений, URL и секреты SHALL быть обязательными — их отсутствие является ошибкой старта. Публичный и внутренний адреса MUST различаться; совпадение SHALL быть ошибкой старта.

#### Scenario: Старт с валидной конфигурацией
- **WHEN** процесс запускается с корректными переменными окружения
- **THEN** сервис начинает слушать публичный и внутренний адреса и пишет в лог факт старта с именем окружения и обоими адресами

#### Scenario: Старт с невалидной конфигурацией
- **WHEN** переменная окружения содержит недопустимое значение (например, нераспознанный уровень логирования)
- **THEN** процесс завершается с ненулевым кодом выхода и понятным сообщением об ошибке, не начиная принимать трафик

#### Scenario: Отсутствие обязательных параметров вне development
- **WHEN** процесс запускается с `APP_ENV=production` без строки подключения PostgreSQL, Redis или секрета RelayState
- **THEN** процесс завершается с ненулевым кодом выхода и сообщением, какие переменные отсутствуют

#### Scenario: Публичный и внутренний адреса совпадают
- **WHEN** внутренний адрес прослушивания равен публичному
- **THEN** процесс завершается с ненулевым кодом выхода и сообщением, что адреса зон должны различаться

## ADDED Requirements

### Requirement: Две зоны прослушивания
Сервис SHALL обслуживать HTTP на двух адресах: публичном (для входного proxy: вход, провижининг, GraphQL, liveness/readiness) и внутреннем (для контура кластера: проверка сессии для ext-auth, метрики, e2e-вход). Маршруты с префиксом `/internal/` SHALL обслуживаться только на внутреннем адресе; на публичном адресе они MUST NOT существовать (404). `GET /healthz` и `GET /readyz` SHALL обслуживаться на публичном адресе. Оба слушателя SHALL запускаться до объявления готовности; невозможность занять любой из адресов SHALL быть ошибкой старта. Graceful shutdown SHALL останавливать оба слушателя в пределах одного настроенного таймаута.

#### Scenario: Внутренний маршрут на публичном адресе
- **WHEN** на публичный адрес приходит запрос к `/internal/session/validate` или `/internal/metrics`
- **THEN** ответ 404, проверка сессии не выполняется, метрики не отдаются

#### Scenario: Внутренний маршрут на внутреннем адресе
- **WHEN** на внутренний адрес приходит запрос к `/internal/session/validate` с cookie действующей сессии
- **THEN** ответ соответствует требованию «Внутренняя проверка сессии» (200 с заголовками контекста)

#### Scenario: Публичный маршрут на внутреннем адресе
- **WHEN** на внутренний адрес приходит запрос к `/auth/me` или `/graphql`
- **THEN** ответ 404

#### Scenario: Внутренний адрес занят
- **WHEN** внутренний адрес не удаётся занять при старте
- **THEN** процесс завершается с ненулевым кодом выхода, публичный слушатель не остаётся работать без внутреннего

#### Scenario: Остановка обоих слушателей
- **WHEN** приходит SIGTERM во время обработки запросов на обоих адресах
- **THEN** новые соединения не принимаются ни на одном адресе, активные запросы обоих завершаются штатно, процесс выходит с кодом 0
