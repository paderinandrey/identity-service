# events-contract

## Why

Контракт событий пользователей существует только как абзац README и
Go-структура `events.Payload`: ни машинно-читаемой схемы, ни примеров, ни
проверки, что payload не разошёлся с описанием. Консьюмеров пока нет, а
интеграция с GSH ([[2026-09-18-gsh-integration]], стадия A) начинается
именно с них: команде GSH нужен документ, по которому пишется обработчик,
и образец поведения — идемпотентность по id события, отбрасывание версии
не выше применённой, первичная загрузка через replay. Обзор GSH показал,
что их inbox-контур дедуплицирует только по id и не сравнивает версии, а
события одного пользователя обрабатывает параллельно, — ровно те
свойства, которые контракт должен проговорить явно. Пункт 16 волны 3 в
[[2026-09-14-triage-and-plan]], репозиторная половина.

## What Changes

- **Опубликованный контракт**: `docs/events/user-events.md` (текст для
  команд-консьюмеров: exchange, routing keys, свойства AMQP, семантика
  типов, обязанности консьюмера, replay), `docs/events/user-event.schema.json`
  (JSON Schema 2020-12 для body) и `docs/events/examples/*.json` — по
  одному примеру на тип события.
- **Golden-тесты**: тест в `internal/events` проверяет, что payload,
  который строит сервис, проходит схему, а примеры совпадают с выводом
  `NewPayload` для фиксированных входов. Изменение payload без обновления
  схемы и примеров ломает сборку. Для проверки схемы добавляется
  test-only зависимость `github.com/santhosh-tekuri/jsonschema/v6`.
- **Референсный консьюмер** `dev/stub-consumer` (отдельный Go-модуль,
  как `dev/stub-subgraph`): владеет своей durable-очередью, привязанной к
  `identity.events` по `user.#`; ведёт проекцию пользователей
  (in-memory, для стенда) с дедупликацией по id события и отбрасыванием
  версии не выше применённой; отдаёт проекцию и счётчики (applied,
  duplicates, stale, rejected) по HTTP. Обработка оформлена так, чтобы её
  можно было переписать на Ruby построчно: разбор → проверка id → сравнение
  версии → запись.
- **Стенд**: стаб-консьюмер как зависимость `values-local.yaml`; шаг
  `stand-verify`: `replay-users` заполняет пустую проекцию всеми
  пользователями с их версиями; SCIM-изменение имени доходит до проекции
  с новой версией; повторный `replay-users` (snapshot с той же версией)
  учитывается как stale и проекцию не меняет.
- README: раздел «User events» ссылается на документ контракта вместо
  дублирования JSON.

Не меняется: сам payload, routing keys, свойства публикации, relay.
Поле `title` (нужно GSH) — отдельный change после мержа `relay-lease`:
он требует миграции, а нумерация миграций сейчас занята PR #6.

## Capabilities

### New Capabilities

Нет.

### Modified Capabilities

- `user-events`: требование «Контракт события» дополняется опубликованной
  схемой и примерами, которые SHALL совпадать с фактическим payload;
  новое требование «Обязанности консьюмера» фиксирует семантику
  at-least-once, дедупликации по id, версии и replay, на которую
  консьюмеры могут опираться.

## Impact

- Новые файлы: `docs/events/*`, `dev/stub-consumer/*`,
  `internal/events/contract_test.go`.
- `go.mod`: test-only зависимость для JSON Schema.
- `charts/identity-service/values-local.yaml`, `scripts/stand-up.sh`
  (сборка образа), `scripts/stand-verify.sh`, `ci-helm-checks.sh`
  (компонент стенда), README.
- Совместимость: контракт описывает существующее поведение; для
  консьюмеров ничего не меняется.
