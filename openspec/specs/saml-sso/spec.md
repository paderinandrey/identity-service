# saml-sso

## Purpose

Вход пользователей через корпоративный Okta по протоколу SAML 2.0: инициация входа, обработка ответа IdP, публикация SP-метаданных и безопасный возврат на исходную страницу. Поведенческий референс — рабочая реализация в GSH.

## Requirements

### Requirement: Инициация входа
Сервис SHALL по `GET /auth/saml/init` перенаправлять браузер на SSO-URL Okta с корректным SAML AuthnRequest. Параметр `next` (относительный путь возврата) SHALL передаваться через подписанный RelayState. Маршрут MUST быть доступен без существующей сессии.

#### Scenario: Переход к IdP
- **WHEN** браузер открывает `/auth/saml/init?next=/orders/42`
- **THEN** сервис отвечает redirect на SSO-URL Okta, а RelayState содержит подписанный путь `/orders/42` с меткой времени

#### Scenario: Опасный next отбрасывается
- **WHEN** `next` является абсолютным URL, protocol-relative URL или содержит перевод строки
- **THEN** в RelayState сохраняется путь `/` вместо переданного значения

### Requirement: Обработка ACS-ответа
Сервис SHALL по `POST /auth/saml/acs` валидировать SAMLResponse: подпись сообщения и assertion (SHA-256), срок действия с допустимым дрейфом часов не более 60 секунд, соответствие destination собственному ACS URL и audience — собственному entity ID, ограничение размера сообщения. При успехе SHALL создаваться сессия и выполняться redirect на путь из RelayState поверх настроенного frontend base URL. Невалидный ответ SHALL отклоняться с 401 без создания сессии.

#### Scenario: Успешный вход
- **WHEN** приходит корректно подписанный SAMLResponse для активного пользователя с валидным RelayState
- **THEN** создаётся серверная сессия, браузер получает session cookie и redirect на сохранённый путь поверх frontend base URL

#### Scenario: Невалидная подпись
- **WHEN** подпись сообщения или assertion не проходит проверку
- **THEN** сервис отвечает 401, сессия не создаётся, содержимое assertion не логируется

#### Scenario: Чужой destination или audience
- **WHEN** destination не совпадает с ACS URL сервиса или audience не содержит его entity ID
- **THEN** ответ отклоняется с 401

#### Scenario: Просроченный RelayState
- **WHEN** RelayState отсутствует, имеет неверную подпись или старше своего TTL
- **THEN** вход продолжается, а путём возврата служит `/`

### Requirement: SP-метаданные
Сервис SHALL по `GET /auth/saml/metadata` отдавать XML собственных SP-метаданных (entity ID, ACS URL, binding HTTP-POST) с корректным content type. Маршрут MUST быть доступен без сессии.

#### Scenario: Получение метаданных
- **WHEN** приходит запрос `GET /auth/saml/metadata`
- **THEN** сервис отвечает 200 с XML, содержащим entity ID и ACS URL сервиса

### Requirement: Конфигурация SP из метаданных IdP
Сервис SHALL строить настройки SAML из метаданных IdP, полученных по настроенному URL (entity ID, SSO URL, сертификаты, включая несколько активных). Недоступность или невалидность метаданных при старте SHALL приводить к отказу запуска, а не к работе с ослабленной проверкой.

#### Scenario: Метаданные недоступны на старте
- **WHEN** URL метаданных IdP не отвечает или возвращает невалидный документ
- **THEN** сервис завершается с ошибкой конфигурации и не начинает принимать трафик

### Requirement: Сопоставление identity с пользователем
Сервис SHALL находить пользователя по внешней идентичности (провайдер, стабильный subject из ответа IdP). Если идентичность неизвестна, SHALL выполняться однократная привязка по email к активному пользователю без существующей идентичности этого провайдера, с сохранением привязки. Неизвестный или неактивный пользователь SHALL получать отказ без создания сессии; JIT-создание пользователей MUST NOT выполняться.

#### Scenario: Повторный вход по сохранённой идентичности
- **WHEN** приходит ответ IdP с subject, уже привязанным к пользователю
- **THEN** пользователь определяется по привязке независимо от текущего email в ответе

#### Scenario: Первый вход существующего пользователя
- **WHEN** subject неизвестен, но email из ответа принадлежит активному пользователю без идентичности этого провайдера
- **THEN** привязка (провайдер, subject) сохраняется и создаётся сессия

#### Scenario: Неизвестный пользователь
- **WHEN** ни subject, ни email не соответствуют активному пользователю
- **THEN** сервис отвечает отказом, сессия и пользователь не создаются

#### Scenario: Деактивированный пользователь
- **WHEN** ответ IdP соответствует пользователю с признаком неактивности
- **THEN** вход отклоняется, существующая привязка не удаляется

### Requirement: Защита секретов SSO
Сервис MUST NOT записывать в логи содержимое SAML assertions, NameID, идентификаторы сессий и значения cookie. Ошибки валидации SHALL логироваться с категорией причины без чувствительных данных.

#### Scenario: Логи при ошибке валидации
- **WHEN** валидация SAMLResponse завершилась ошибкой
- **THEN** в логе присутствует категория причины и отсутствуют содержимое assertion и NameID
