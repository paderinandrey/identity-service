# service-runtime

## Purpose

Базовое поведение процесса Identity & Access Service: запуск с конфигурацией из окружения, health/readiness эндпоинты для Kubernetes, структурированное логирование и корректное завершение работы.

## Requirements

### Requirement: Запуск с конфигурацией из окружения
Сервис SHALL читать конфигурацию из переменных окружения при старте: публичный адрес прослушивания HTTP, внутренний адрес прослушивания HTTP, имя окружения (development/staging/production), уровень логирования, строки подключения PostgreSQL и Redis, базовый URL сервиса, URL метаданных IdP, секрет подписи RelayState, базовый URL frontend и параметры сессий (имя cookie, idle-timeout, абсолютный срок, лимит одновременных сессий). Для отсутствующих переменных SHALL применяться безопасные значения по умолчанию, пригодные для локальной разработки; вне development параметры подключений, URL и секреты SHALL быть обязательными — их отсутствие является ошибкой старта. Вне development секрет подписи RelayState SHALL быть не короче 32 символов и не совпадать с dev-значением по умолчанию. При запуске внутри Kubernetes имя окружения SHALL быть задано явно: его отсутствие является ошибкой старта, а не development по умолчанию. Публичный и внутренний адреса MUST различаться; совпадение SHALL быть ошибкой старта.

#### Scenario: Старт с валидной конфигурацией
- **WHEN** процесс запускается с корректными переменными окружения
- **THEN** сервис начинает слушать публичный и внутренний адреса и пишет в лог факт старта с именем окружения и обоими адресами

#### Scenario: Старт с невалидной конфигурацией
- **WHEN** переменная окружения содержит недопустимое значение (например, нераспознанный уровень логирования)
- **THEN** процесс завершается с ненулевым кодом выхода и понятным сообщением об ошибке, не начиная принимать трафик

#### Scenario: Отсутствие обязательных параметров вне development
- **WHEN** процесс запускается с `APP_ENV=production` без строки подключения PostgreSQL, Redis или секрета RelayState
- **THEN** процесс завершается с ненулевым кодом выхода и сообщением, какие переменные отсутствуют

#### Scenario: Слабый секрет RelayState вне development
- **WHEN** процесс запускается с `APP_ENV=staging` и секретом RelayState короче 32 символов или равным dev-значению по умолчанию
- **THEN** процесс завершается с ошибкой конфигурации

#### Scenario: APP_ENV не задан в Kubernetes
- **WHEN** процесс запускается в поде Kubernetes без переменной `APP_ENV`
- **THEN** процесс завершается с ошибкой конфигурации, не переходя в development

#### Scenario: Публичный и внутренний адреса совпадают
- **WHEN** внутренний адрес прослушивания равен публичному
- **THEN** процесс завершается с ненулевым кодом выхода и сообщением, что адреса зон должны различаться

### Requirement: Liveness-эндпоинт
Сервис SHALL отвечать на `GET /healthz` статусом 200, пока процесс жив и способен обрабатывать HTTP-запросы. Эндпоинт MUST NOT зависеть от внешних систем.

#### Scenario: Проверка liveness
- **WHEN** приходит запрос `GET /healthz`
- **THEN** сервис отвечает 200 с телом, указывающим статус ok

### Requirement: Readiness-эндпоинт
Сервис SHALL отвечать на `GET /readyz` статусом 200, когда готов принимать трафик: HTTP-сервер запущен, подключения к PostgreSQL и Redis установлены и проходят проверку. После начала graceful shutdown или при потере обязательной зависимости endpoint SHALL возвращать 503.

#### Scenario: Сервис готов
- **WHEN** сервис запущен, PostgreSQL и Redis доступны и не идёт остановка
- **THEN** `GET /readyz` возвращает 200

#### Scenario: Сервис останавливается
- **WHEN** сервис получил сигнал остановки и начал graceful shutdown
- **THEN** `GET /readyz` возвращает 503, чтобы балансировщик прекратил направлять новые запросы

#### Scenario: Потеря зависимости
- **WHEN** проверка подключения к PostgreSQL или Redis не проходит
- **THEN** `GET /readyz` возвращает 503, при этом `GET /healthz` продолжает отвечать 200

### Requirement: Graceful shutdown
При получении SIGTERM или SIGINT сервис SHALL прекратить приём новых соединений, дождаться завершения активных запросов в пределах настроенного таймаута и завершиться с нулевым кодом выхода.

#### Scenario: Остановка с активными запросами
- **WHEN** приходит SIGTERM во время обработки запросов
- **THEN** активные запросы завершаются штатно, новые соединения не принимаются, процесс выходит с кодом 0

#### Scenario: Превышение таймаута остановки
- **WHEN** активные запросы не завершились в пределах таймаута shutdown
- **THEN** сервис принудительно закрывает соединения и завершается, зафиксировав это в логе

### Requirement: Структурированное логирование
Сервис SHALL писать логи в структурированном JSON-формате в stdout, включая уровень, время и сообщение. Уровень логирования SHALL управляться конфигурацией.

#### Scenario: Фильтрация по уровню
- **WHEN** установлен уровень логирования `info`
- **THEN** записи уровня `debug` не попадают в вывод, записи `info` и выше — попадают

### Requirement: Две зоны прослушивания
Сервис SHALL обслуживать HTTP на двух адресах: публичном (для входного proxy: вход, провижининг, GraphQL, liveness/readiness) и внутреннем (для контура кластера: проверка сессии для ext-auth, метрики, e2e-вход). Маршруты с префиксом `/internal/` SHALL обслуживаться только на внутреннем адресе; на публичном адресе они MUST NOT существовать (404). `GET /healthz` и `GET /readyz` SHALL обслуживаться на публичном адресе. Оба слушателя SHALL запускаться до объявления готовности; невозможность занять любой из адресов SHALL быть ошибкой старта. Graceful shutdown SHALL останавливать оба слушателя в пределах одного настроенного таймаута.

#### Scenario: Внутренний маршрут на публичном адресе
- **WHEN** на публичный адрес приходит запрос к `/internal/session/validate` или `/internal/metrics`
- **THEN** ответ 404, проверка сессии не выполняется, метрики не отдаются

#### Scenario: Внутренний маршрут на внутреннем адресе
- **WHEN** на внутренний адрес приходит запрос к `/internal/session/validate` с cookie действующей сессии
- **THEN** ответ соответствует требованию «Внутренняя проверка сессии» (200 с заголовками контекста)

#### Scenario: Публичный маршрут на внутреннем адресе
- **WHEN** на внутренний адрес приходит запрос к `/auth/me` или `/graphql`
- **THEN** ответ 404

#### Scenario: Внутренний адрес занят
- **WHEN** внутренний адрес не удаётся занять при старте
- **THEN** процесс завершается с ненулевым кодом выхода, публичный слушатель не остаётся работать без внутреннего

#### Scenario: Остановка обоих слушателей
- **WHEN** приходит SIGTERM во время обработки запросов на обоих адресах
- **THEN** новые соединения не принимаются ни на одном адресе, активные запросы обоих завершаются штатно, процесс выходит с кодом 0
