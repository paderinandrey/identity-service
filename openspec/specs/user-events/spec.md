# user-events

## Purpose

Надёжная доставка изменений пользователей в бизнес-сервисы: транзакционный outbox в PostgreSQL, публикация в RabbitMQ, версия профиля против устаревших обновлений и replay для первоначальной загрузки и восстановления проекций.

## Requirements

### Requirement: Транзакционная запись событий
Каждое изменение пользователя (создание, изменение email/имени, деактивация, реактивация) SHALL записывать событие в outbox в той же транзакции базы данных, что и само изменение. Откат транзакции MUST NOT оставлять событие. Изменение `last_sign_in_at` событием не является.

#### Scenario: Событие вместе с изменением
- **WHEN** SCIM-запрос меняет email пользователя
- **THEN** в outbox появляется событие `identity.user.updated` в той же транзакции, с новым email в payload

#### Scenario: Откат не оставляет события
- **WHEN** транзакция изменения пользователя откатывается
- **THEN** событие в outbox отсутствует

### Requirement: Версия профиля
Пользователь SHALL иметь монотонно растущую версию, увеличиваемую при каждом изменении профиля или признака активности. Версия SHALL входить в payload каждого события, чтобы консьюмеры отбрасывали устаревшие обновления при нарушении порядка доставки.

#### Scenario: Версия растёт с каждым изменением
- **WHEN** пользователь изменён дважды подряд
- **THEN** второе событие несёт версию строго больше первой

### Requirement: Контракт события
Событие SHALL содержать: уникальный стабильный id, тип (`identity.user.created|updated|deactivated|reactivated|snapshot`), schemaVersion, момент возникновения и снимок пользователя (глобальный UUID, email, имя, признак активности, версия). Сообщение SHALL публиковаться персистентно в durable topic-exchange с routing key, равным типу события без префикса `identity.`, и свойствами `message_id` (id события) и `type`. Контракт SHALL быть опубликован в репозитории как машинно-читаемая схема тела сообщения и примеры каждого типа; фактический payload сервиса SHALL проходить эту схему, а примеры SHALL совпадать с payload для тех же входов — расхождение является ошибкой сборки.

#### Scenario: Payload деактивации
- **WHEN** пользователь деактивируется через SCIM
- **THEN** публикуется `identity.user.deactivated` с его UUID, active=false и текущей версией

#### Scenario: Payload соответствует опубликованной схеме
- **WHEN** сервис строит payload любого типа события
- **THEN** payload проходит опубликованную JSON Schema, а пример этого типа в репозитории байт-в-байт равен payload для зафиксированных входов

#### Scenario: Изменение payload без обновления контракта
- **WHEN** в payload добавлено или переименовано поле, а схема и примеры не обновлены
- **THEN** проверка контракта в сборке завершается ошибкой

### Requirement: Надёжная публикация
Публикатор SHALL доставлять события из outbox с подтверждением брокера, помечать опубликованные и повторять неудачные с ограниченным backoff, не блокируя новые события. Неопубликованные события SHALL переживать перезапуск сервиса; события одного пользователя SHALL публиковаться в порядке их записи.

#### Scenario: Брокер временно недоступен
- **WHEN** RabbitMQ недоступен в момент изменения пользователя
- **THEN** изменение выполняется, событие остаётся в outbox и публикуется после восстановления брокера

#### Scenario: Публикация после рестарта
- **WHEN** сервис перезапущен с неопубликованными событиями в outbox
- **THEN** события публикуются после старта без участия оператора

### Requirement: Replay для загрузки проекций
Сервис SHALL предоставлять CLI-команду постановки snapshot-событий всех пользователей в outbox для первоначальной загрузки проекции или восстановления после потерь. Snapshot SHALL несёт текущую версию пользователя и SHALL быть безопасен для повторной обработки консьюмерами.

#### Scenario: Полный replay
- **WHEN** оператор запускает команду replay
- **THEN** для каждого пользователя в outbox появляется `identity.user.snapshot` с его текущим состоянием и версией

### Requirement: Обязанности консьюмера
Доставка SHALL считаться at-least-once без гарантии порядка между сообщениями, включая события одного пользователя, обработанные параллельно. Опубликованный контракт SHALL предписывать консьюмеру: владеть своей durable-очередью, привязанной к exchange по `user.#`; дедуплицировать по id события; применять снимок пользователя только если его версия строго больше применённой для этого пользователя, атомарно с записью проекции; трактовать `snapshot` так же, как остальные типы; загружать и восстанавливать проекцию через replay. Референсная реализация этих правил SHALL входить в репозиторий и проверяться тестами.

#### Scenario: Дубликат по id
- **WHEN** консьюмер получает сообщение с уже обработанным id события
- **THEN** проекция не меняется, сообщение подтверждается

#### Scenario: Устаревшая версия
- **WHEN** консьюмер получает событие с версией не больше применённой для этого пользователя
- **THEN** проекция не меняется, сообщение подтверждается и учитывается как устаревшее

#### Scenario: Параллельные события одного пользователя
- **WHEN** два события одного пользователя с версиями N и N+1 обрабатываются одновременно в любом порядке
- **THEN** проекция в итоге содержит состояние версии N+1

#### Scenario: Replay на пустую проекцию
- **WHEN** оператор запускает replay при пустой проекции консьюмера
- **THEN** проекция содержит каждого пользователя с его текущей версией; повторный replay ничего не меняет
