# web-sessions

## Purpose

Серверные браузерные сессии в Redis: единственный держатель состояния аутентификации для всей экосистемы. Браузер хранит только непрозрачный идентификатор в HttpOnly cookie; проверка сессии предоставляется внутренним API для ext-auth входного proxy.

## Requirements

### Requirement: Создание сессии при входе
При успешном SAML-входе сервис SHALL создавать сессию в Redis с непредсказуемым идентификатором и выдавать его в cookie с атрибутами `HttpOnly`, `Secure` (вне development), `SameSite=Lax` и согласованным `Path`. Идентификатор сессии SHALL ротироваться при каждом входе; данные сессии SHALL включать идентификатор пользователя и время создания. Пароли и токены MUST NOT попадать в cookie или localStorage.

#### Scenario: Cookie после входа
- **WHEN** пользователь успешно вошёл через SAML
- **THEN** браузер получает cookie c непрозрачным идентификатором и атрибутами HttpOnly, SameSite=Lax и Secure вне development

#### Scenario: Ротация при повторном входе
- **WHEN** пользователь с действующей сессией снова проходит вход
- **THEN** прежний идентификатор сессии перестаёт действовать, выдаётся новый

### Requirement: Срок жизни сессии
Сессия SHALL истекать по idle-timeout (продлевается активностью) и по абсолютному сроку жизни; оба значения конфигурируются. Истёкшая сессия SHALL считаться недействительной без обращения к другим системам.

#### Scenario: Истечение по бездействию
- **WHEN** с момента последней активности прошло больше idle-timeout
- **THEN** сессия недействительна, запросы с её cookie получают 401

#### Scenario: Абсолютный срок
- **WHEN** с момента создания сессии прошло больше абсолютного срока жизни
- **THEN** сессия недействительна независимо от активности

### Requirement: Завершение сессии
Сервис SHALL по `POST /auth/logout` удалять серверную сессию и сбрасывать cookie. Запрос SHALL приниматься только методом POST; для защиты от CSRF SHALL проверяться заголовок Origin (или Sec-Fetch-Site) на соответствие разрешённым источникам.

#### Scenario: Выход
- **WHEN** аутентифицированный пользователь отправляет `POST /auth/logout` с корректным Origin
- **THEN** серверная сессия удаляется, cookie сбрасывается, повторные запросы с прежним идентификатором получают 401

#### Scenario: Кросс-доменный logout отклоняется
- **WHEN** `POST /auth/logout` приходит с чужим Origin
- **THEN** сервис отвечает отказом и сессию не удаляет

### Requirement: Лимит одновременных сессий
Число одновременных сессий одного пользователя SHALL ограничиваться конфигурируемым значением; вход сверх лимита SHALL вытеснять самые старые сессии пользователя.

#### Scenario: Вытеснение старейшей сессии
- **WHEN** пользователь входит, уже имея максимальное число сессий
- **THEN** новая сессия создаётся, а самая старая перестаёт действовать

### Requirement: Текущий пользователь
Сервис SHALL по `GET /auth/me` возвращать данные пользователя текущей сессии (глобальный ID, email, имя). Без действительной сессии ответ SHALL быть 401.

#### Scenario: Запрос с действующей сессией
- **WHEN** приходит `GET /auth/me` с валидной session cookie
- **THEN** сервис отвечает 200 с глобальным ID, email и именем пользователя

#### Scenario: Запрос без сессии
- **WHEN** приходит `GET /auth/me` без cookie или с недействительной сессией
- **THEN** сервис отвечает 401

### Requirement: Внутренняя проверка сессии
Сервис SHALL предоставлять внутренний HTTP endpoint проверки сессии для ext-auth входного proxy по пути `/internal/session/validate`, обслуживаемый только на внутреннем адресе прослушивания (см. `service-runtime`, «Две зоны прослушивания»). Endpoint SHALL отвечать независимо от HTTP-метода запроса и независимо от того, дописан ли к пути суффикс исходного запроса: ext-auth воспроизводит метод исходного запроса и трактует настроенный путь как префикс, поэтому привязка к одному методу или к точному пути отклоняла бы проверку для всех запросов. По cookie из запроса он SHALL возвращать 200 с контекстом пользователя (глобальный ID, email) и его эффективными правами в формате `application:permission` (через запятую) в ответных заголовках либо 401. Заголовок прав SHALL присутствовать в каждом ответе 200, в том числе пустым. Недоступность зависимостей MUST NOT приводить к ответу 200 (fail-close). Endpoint MUST NOT быть достижим через публичную маршрутизацию и MUST NOT существовать на публичном адресе прослушивания.

#### Scenario: Валидная сессия
- **WHEN** proxy передаёт запрос с cookie действующей сессии активного пользователя
- **THEN** ответ 200 содержит заголовки с глобальным ID, email и эффективными правами пользователя

#### Scenario: Проверка методом исходного запроса
- **WHEN** ext-auth обращается к endpoint методом POST (зеркалируя `POST /graphql`) с cookie действующей сессии
- **THEN** ответ такой же, как для GET: 200 с заголовками контекста

#### Scenario: Путь с дописанным суффиксом исходного запроса
- **WHEN** ext-auth обращается по пути `/internal/session/validate/graphql` (настроенный путь как префикс плюс исходный) с cookie действующей сессии
- **THEN** ответ такой же, как для точного пути: 200 с заголовками контекста

#### Scenario: Пользователь без назначенных ролей
- **WHEN** у пользователя действующей сессии нет ни одной роли
- **THEN** ответ 200 содержит идентификационные заголовки и пустой заголовок прав

#### Scenario: Недействительная сессия
- **WHEN** cookie отсутствует, сессия истекла или пользователь деактивирован
- **THEN** ответ 401 без контекста пользователя

#### Scenario: Redis недоступен
- **WHEN** хранилище сессий недоступно при проверке
- **THEN** ответ является ошибкой, а не 200; запрос не пропускается как авторизованный

#### Scenario: Обращение на публичный адрес
- **WHEN** запрос к `/internal/session/validate` приходит на публичный адрес прослушивания с cookie действующей сессии
- **THEN** ответ 404 без заголовков контекста

### Requirement: Деактивация пользователя завершает доступ
Проверка сессии SHALL учитывать актуальный признак активности пользователя: сессии деактивированного пользователя SHALL считаться недействительными не позднее конфигурируемой задержки отзыва. Деактивация SHALL поднимать поколение сессий пользователя в той же транзакции, что снимает признак активности, поэтому реактивация MUST NOT возвращать действительность прежним сессиям.

#### Scenario: Сессия деактивированного пользователя
- **WHEN** пользователь деактивирован, а его сессия ещё не истекла
- **THEN** внутренняя проверка сессии и `GET /auth/me` отвечают 401 не позднее задержки отзыва

#### Scenario: Реактивация не возвращает сессии
- **WHEN** деактивированный пользователь реактивирован, а прежний идентификатор его сессии предъявляется снова
- **THEN** проверка сессии и `GET /auth/me` отвечают 401; доступ возможен только после нового входа

### Requirement: Уничтожение всех сессий пользователя
Сервис SHALL поддерживать немедленное уничтожение всех сессий пользователя: сначала SHALL устанавливаться ограждение по поколению, затем удаляться сессии по индексу. Операция SHALL использоваться при деактивации через провижининг. После уничтожения прежние идентификаторы сессий SHALL быть недействительны, в том числе для запросов, загрузивших сессию до отзыва: устаревшая сессия MUST NOT загружаться и MUST NOT сохраняться повторно. Недоступность хранилища сессий при отзыве MUST NOT отменять отзыв, уже записанный в базе данных.

#### Scenario: Все сессии отозваны
- **WHEN** для пользователя с несколькими активными сессиями вызывается уничтожение всех сессий
- **THEN** каждый прежний идентификатор сессии получает 401, индекс сессий пользователя пуст

#### Scenario: Запрос в полёте не восстанавливает сессию
- **WHEN** запрос загрузил действующую сессию, затем все сессии пользователя отозваны, затем запрос завершается и сессия сохраняется
- **THEN** сохранение устаревшей сессии не выполняется, а следующий запрос с тем же идентификатором получает 401

#### Scenario: Отказ хранилища сессий при отзыве
- **WHEN** отзыв записан в базе данных, а удалить сессии из хранилища не удалось
- **THEN** проверка сессии при недоступном хранилище отвечает 503, а после его восстановления прежние идентификаторы отклоняются не позднее задержки отзыва

### Requirement: Ограниченная свежесть контекста пользователя
Данные пользователя (email, имя, признак активности), возвращаемые в `GET /auth/me` и во внутренней проверке сессии, MAY кешироваться и отставать от базы не более чем на конфигурируемую задержку отзыва. Проверка сессии на прогретом кеше MUST NOT обращаться к базе данных, чтобы не нагружать её на каждом запросе экосистемы.

#### Scenario: Повторные проверки не ходят в базу
- **WHEN** для одного пользователя подряд выполняется несколько проверок сессии в пределах задержки отзыва
- **THEN** к хранилищу пользователей происходит не более одного обращения

#### Scenario: Изменение профиля доходит после истечения задержки
- **WHEN** email пользователя изменён в базе, а с момента предыдущей проверки прошло больше задержки отзыва
- **THEN** следующая проверка возвращает новый email

### Requirement: Поколение сессий пользователя
Сервис SHALL хранить у пользователя поколение сессий — монотонный счётчик отзыва в базе данных. Сессия при создании SHALL запоминать текущее поколение пользователя, и SHALL считаться действительной только пока её поколение равно текущему. Поколение SHALL зеркалиться в хранилище сессий как ограждение, проверяемое при каждой загрузке и каждом сохранении сессии. Сессии, созданные до появления поколения, SHALL трактоваться как поколение 0 и оставаться действительными до первого отзыва у пользователя. Ограждение SHALL только расти: ни вход, прочитавший устаревшее поколение, ни запоздавший отзыв с меньшим поколением MUST NOT опускать его. Проверка ограждения и запись сессии SHALL выполняться как одна атомарная операция хранилища.

#### Scenario: Вход после отзыва
- **WHEN** у пользователя отозваны все сессии, и он входит заново
- **THEN** новая сессия получает текущее поколение и действительна; прежние идентификаторы сессий остаются недействительными

#### Scenario: Сессия без поколения
- **WHEN** загружается сессия, созданная до введения поколения, а у пользователя поколение 0
- **THEN** сессия действительна; после первого отзыва она отклоняется

#### Scenario: Вход проиграл гонку отзыву
- **WHEN** вход прочитал поколение N, а до создания сессии пользователю отозвали сессии с поколением N+1
- **THEN** ограждение остаётся N+1, вход отклоняется, сессия не выдаётся

#### Scenario: Запоздавший отзыв с меньшим поколением
- **WHEN** после отзыва с поколением N+1 приходит отзыв с поколением N
- **THEN** ограждение остаётся N+1; сессии поколения N+1 продолжают действовать

### Requirement: Доверенный источник контекста
Заголовки контекста пользователя, доходящие до защищённого upstream, SHALL быть значениями из ответа проверки сессии. Одноимённые заголовки, присланные клиентом, MUST NOT доходить до upstream ни в каком виде — ни при непустом, ни при пустом значении из проверки. Внутренний адрес прослушивания SHALL быть доступен по сети только входному proxy, системе мониторинга и явно перечисленным в конфигурации развёртывания источникам; из прочих подов кластера соединение SHALL отклоняться на сетевом уровне. Публичный адрес SHALL быть доступен только входному proxy и явно перечисленным источникам (например, GraphQL Router).

#### Scenario: Подделанный идентификатор пользователя
- **WHEN** клиент с действующей сессией отправляет защищённый запрос с собственным заголовком `X-Identity-User-Id`
- **THEN** upstream получает идентификатор пользователя сессии, а не присланное клиентом значение

#### Scenario: Подделанные права у пользователя без ролей
- **WHEN** клиент с действующей сессией пользователя без ролей отправляет защищённый запрос с собственным заголовком `X-Identity-Permissions`
- **THEN** upstream получает пустой заголовок прав, присланное клиентом значение не доходит

#### Scenario: Прямое обращение из неразрешённого пода
- **WHEN** под кластера, не входящий в разрешённые источники, обращается к внутреннему адресу сервиса
- **THEN** соединение не устанавливается

#### Scenario: Обращение из разрешённого источника
- **WHEN** входной proxy или явно разрешённый под обращается к внутреннему адресу сервиса
- **THEN** соединение устанавливается и проверка сессии отвечает по контракту
