# graphql-api

## Purpose

GraphQL-сабграф identity-service: профили пользователей, справочник приложений/ролей/permissions и управление назначениями за общим GraphQL Router, с федеративной ссылкой на пользователей из других сабграфов.

## Requirements

### Requirement: GraphQL endpoint с аутентификацией по сессии
Сервис SHALL обслуживать GraphQL-запросы на `POST /graphql`, аутентифицируя вызывающего по браузерной cookie-сессии. Запрос без действительной сессии SHALL получать ошибку с кодом `UNAUTHENTICATED` без каких-либо данных. Introspection и сам endpoint MUST NOT раскрывать данные неаутентифицированным вызывающим.

#### Scenario: Запрос без сессии
- **WHEN** приходит GraphQL-запрос без cookie или с недействительной сессией
- **THEN** ответ содержит ошибку `UNAUTHENTICATED` и не содержит данных

#### Scenario: Запрос с действующей сессией
- **WHEN** аутентифицированный пользователь запрашивает `me`
- **THEN** ответ содержит его глобальный ID, email, имя и эффективные права

### Requirement: Справочник пользователей и приложений
Аутентифицированный пользователь SHALL иметь возможность запрашивать: список активных пользователей с поиском по имени или email, отдельного пользователя по ID, список приложений с их ролями и permissions. Деактивированные пользователи SHALL попадать в выдачу только по явному запросу (для истории и аудита).

#### Scenario: Поиск пользователей
- **WHEN** запрошен `users(search: "ann")`
- **THEN** возвращаются активные пользователи, чьё имя или email содержит подстроку без учёта регистра

#### Scenario: Справочник приложений
- **WHEN** запрошены `applications` с ролями и permissions
- **THEN** возвращается полный справочник, у ролей виден их состав

### Requirement: Мутации назначений с авторизацией
Мутации `grantRole` и `revokeRole` SHALL выполняться только вызывающими с permission `identity:access.manage`; остальные SHALL получать ошибку `FORBIDDEN` без изменения данных. Успешная мутация SHALL быть идемпотентной и записываться в журнал изменений доступа с актором — вызывающим пользователем.

#### Scenario: Назначение с правом управления
- **WHEN** пользователь с `identity:access.manage` выполняет `grantRole`
- **THEN** назначение создаётся, журнал содержит запись с его глобальным ID как актором

#### Scenario: Назначение без права управления
- **WHEN** аутентифицированный пользователь без `identity:access.manage` выполняет `grantRole`
- **THEN** ответ содержит ошибку `FORBIDDEN`, назначение не создаётся, журнал не пополняется

#### Scenario: Несуществующая роль
- **WHEN** `grantRole` вызывается с неизвестной ролью
- **THEN** возвращается понятная ошибка, данные не меняются

### Requirement: Чтение журнала изменений доступа
Запрос журнала изменений доступа SHALL требовать permission `identity:access.manage` и SHALL возвращать записи от новых к старым с ограничением количества.

#### Scenario: Журнал для администратора доступа
- **WHEN** пользователь с `identity:access.manage` запрашивает `accessAuditLog(limit: 10)`
- **THEN** возвращаются до 10 последних записей с актором, действием и временем

#### Scenario: Журнал без права
- **WHEN** пользователь без `identity:access.manage` запрашивает журнал
- **THEN** ответ содержит ошибку `FORBIDDEN` без записей

### Requirement: Federation-совместимость
Схема SHALL быть валидным сабграфом Apollo Federation v2: тип `User` объявлен entity с ключом `id`, сервис SHALL отвечать на служебные запросы федерации (`_service` с SDL, `_entities` по ключу пользователя), чтобы сабграфы GSH/DFM могли ссылаться на пользователей по глобальному ID.

#### Scenario: SDL для композиции
- **WHEN** запрошен `_service { sdl }`
- **THEN** возвращается SDL с федеративными директивами и entity `User`

#### Scenario: Разрешение entity по ключу
- **WHEN** запрошены `_entities` с представлением `User` по существующему `id`
- **THEN** возвращается пользователь с его полями
